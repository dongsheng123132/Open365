# Open365 架构约定（加功能前先看这页）

一句话：**每个功能 = 一个独立引擎文件，互不依赖。** 这是本项目最重要的维护纪律。

## 为什么这样设计

电脑维护工具会长期不断加功能。如果功能之间互相调用、共享状态，
加到第 10 个功能时就会牵一发动全身、不敢改、不敢删。
所以 Open365 用最朴素的办法保证可维护：**物理隔离**。

## 三条铁律

1. **引擎之间零引用**
   `engine/*.ps1` 之间**不准** dot-source、import、互相调用。
   想验证：`grep -nE "engine|Import-|source" engine/*.ps1` 不应出现跨引擎引用。
   一个引擎删掉，其余必须照常工作。

2. **每个引擎是一个自洽的 CLI**
   - 顶部一个 `param(...)`，第一个位置参数是 action（带 `[ValidateSet(...)]`）。
   - 默认 action 必须是**只读**的（如 `check` / `diagnose` / `list` / `status`），
     先让用户看清楚再动手。
   - 改动系统的 action 才 `Require-Admin`，且尽量**可还原**。
   - 一律支持 `-Json` 输出结构化结果（给未来 GUI / 自动化用）。
   - 小辅助函数（`Test-Admin` / `Write-Step` 等）**各自带一份**，
     **不抽公共库**——5 行琐碎代码，复制优于耦合。

3. **接入主程序只碰两个地方，各加一行**
   `open365.ps1` 里：
   - 命令分发 `switch` 加 1 行：`'foo' { Run-Engine 'foo.ps1' $argv }`
   - 主菜单加 1 个 `[n]` 项 + 对应的 case。
   不在主程序里写任何业务逻辑——主程序只是"按钮面板"。

## 加一个新功能的步骤

1. 新建 `engine/<名字>.ps1`，照上面的"自洽 CLI"模板写。
2. 跑 `tools/add-bom.ps1`（Windows PowerShell 5.x 读中文必须带 UTF-8 BOM）。
3. `engine/<名字>.ps1 help` 能单独跑通 = 独立性达标。
4. 在 `open365.ps1` 加那 2 行接入。
5. 在 `tests/` 加一个**模拟故障→验证修复→自动还原**的自测。
6. README 功能表 + 命令清单 + 路线图各补一行。

## 反例（不要这样做）

- ❌ 在 focus.ps1 里 `& engine/security.ps1`（引擎互调 → 耦合）。
- ❌ 抽 `engine/_common.ps1` 让所有引擎 dot-source 它（一改全崩）。
- ❌ 在 open365.ps1 里直接写注册表/netsh（业务逻辑漏进调度器）。
- ❌ 默认 action 就改系统（应先只读体检，再让用户决定）。
